Architectural Review — svsim (second review)

Reviewed 2026-07-06 against main @ 1b08d69 · canonical copy: plans/in-progress/architectural-review.md · predecessor campaign: plans/completed/2026-07-06-architectural-review.md

This review was taken immediately after the completed seven-step campaign. The debts of organization — the sim.rs god module, three divergent constant evaluators, an unverifiable corpus, untruthful docs — are gone. What remains expensive is different in kind: the runtime evaluation model is the dominant carrying cost (a release build simulates an 8×8 register file at 4 steps/second and the test gate pays for it on every run), the parameterization story is split-brain (per-instance values exist at elaboration, but shapes and unrolled loops silently freeze lowering-time defaults), and the negative corpus is not gated at all. Order of attack: close the verification gap first, fence the parameterization trap, then finish the runtime's own half-completed migration to indexed frames before splitting the last monolith and threading spans through diagnostics.

Simulation speed is now the binding constraint: it sets the price of the gate, forced picorv32 to a curated subset, and caps corpus growth. The slowest suites are not the biggest designs — an 8×8 register file at 4 Hz in release is an algorithmic signal, not a constant-factor one.

Structurally sound elements (do-not-break list)

The compile pipeline and its ownership boundaries

sv-parser types stop at frontend/; HIR is owned; validate.rs is validation-only; elaboration owns parameter resolution. No layer reaches backward.

One shared expression evaluator

expr_eval.rs is the only home of expression semantics; const contexts call the runtime evaluator, so const/runtime cannot diverge. Short-circuit &&/|| is deliberate and load-bearing (picorv32 generate pruning).

The corpus gate

cargo test is the single verification command; empty corpus dirs fail loudly; committed reports are regenerable artifacts. Every step below stands on this.

Four-state core, two-state host boundary

LogicValue inside, BitValue at JSON/CLI edges, converters isolated in sim/value.rs. Locked decision; still correct.

The sim/ split and logic_ops.rs truth tables

Six focused files with pub(super) seams; the split pattern is proven and reused verbatim by step 5 below.

Thin CLI

242 lines of clap-based wrapping over library APIs, per AGENTS.md.

Structural risks and costs (ranked by carrying cost)

1The settle loop does quadratic work through string-keyed adapter tables

Evidence. sim/session.rs:291: iteration budget ∝ design size (summed recursively) × 8; each iteration clones the whole design frame (frame.to_vec()) and detects convergence by deep comparison — while the changed flag the pass already computes is discarded (let _changed = …). Each pass rebuilds HashMap<String, Value> tables from the indexed frame via build_instance_value_table (sim/state.rs:341) — once for the module (session.rs:375), twice more per child per pass (:447, :471), twice per step phase (:498, :513) — cloning every name and value each time. Measured: regfile_8x8 4 steps/s, adder_cs_64bit 1 step/s, release build; the two regfile suites alone are 22 s of the 59 s corpus.

Consequence. Per-step cost grows ~quadratically with design size. The gate costs ~2 minutes on every run; picorv32 stays a curated subset; larger designs are blocked.

Fix direction. A half-finished migration, not a redesign: the indexed frame (RuntimeObjectLayout, ObjectValue) already exists as storage — the compute layer never adopted it. Let evaluation read/write the frame through a small resolver seam; replace clone-and-compare convergence with the existing change tracking. step_hz in docs/tests/ is a built-in benchmark. Not needed: event scheduler, dependency graphs, or behavior change.

2Split-brain parameterization: shapes and unrolled loops freeze defaults

Evidence. HIR stores selects/ranges as concrete usize (hir.rs:210); elaboration derives shapes from those frozen widths (elaborate.rs:252). Procedural for loops are fully unrolled at lowering time against default parameter values (sv_parser.rs:1716). Since the first campaign, parameter values are per-instance at elaboration — so an override affects expressions but not widths, memory shapes, or unrolled bodies. A module whose loop bound or port range depends on an overridden parameter silently simulates with the default. Only 3 corpus files use #( overrides today (value-only), so the trap is latent.

Consequence. A silent-wrong-answer bug class directly on the corpus-growth path: importing any parameterized real-world core can trip it, and the failure is wrong results, not an error.

Fix direction. Fence first: elaboration rejects overrides that feed frozen constructs (ranges, loop bounds) unless equal to the default, with a parameter-naming diagnostic; add negative-corpus cases. The full fix (ranges/bounds as Expr, resolved at elaboration) waits for a real use case — do not build it speculatively.

3The negative corpus is not gated

Evidence. parts/failing/ holds 6 intentional-failure suites; corpus_gate.rs excludes it and nothing in cargo test runs it — only the manual test-fails.sh. A regression that makes duplicate_instance_names.sv compile cleanly passes CI silently.

Consequence. The entire diagnostic surface (validate.rs, frontend unsupported() paths) has no regression protection — the same "verification only when a human remembers" class as the first review's sap2-report finding.

Fix direction. Add must-fail tests to corpus_gate.rs asserting each suite fails and the message still names the expected construct. Retire or thin test-fails.sh. An afternoon of work that protects steps 2, 4, and 6.

4frontend/sv_parser.rs is the last monolith — and hides an elaboration engine

Evidence. 3,563 production lines (next largest: 956), ~90 functions in five clusters: module/port/parameter lowering, statements, expressions/literals, span plumbing, and a loop-unrolling substitution engine (substitute_stmt_ident, module_with_const_binding, …, ~lines 1960–2140) that exists because HIR cannot represent loops or dynamic selects — the mechanism behind risk 2.

Consequence. Every language feature lands in one 3.5k-line file; the unroller's true nature (elaboration in exile) is invisible — which is how risk 2 stayed hidden.

Fix direction. Mechanical split into frontend/sv_parser/ using the proven sim/ pattern, with loop_unroll.rs named for what it is and its doc header stating the default-freezing behavior. No behavior change, no new IR.

5Diagnostics are stringly typed and often span-less

Evidence. diag.rs is 31 lines: three bare-String variants, span: Option<SourceSpan>. 58 of 163 unsupported() calls in the frontend pass None; every Error::Resolve from width.rs/expr_eval.rs carries no location; convergence failures name only the module.

Consequence. Corpus debugging happens by grep; as imported cores grow, time-to-locate dominates time-to-fix.

Fix direction. Not a framework: thread the Locate call sites already hold into the span-less calls; prefix evaluator/width errors with module + construct. Mechanical and incrementally useful.

Smaller frictions

  • test.bat is stale in exactly the class the first review fixed in test.sh: misses sap2/sap3/simple8 and invokes svsim.exe, a binary the workspace doesn't produce. Fix or delete.
  • wiki/architecture/workspace-map.md:34 still credits width.rs with helpers deleted in the first campaign.
  • No root README.md — the repo has no human front door.
  • Zero doc-tests on a deliberately public API (~40 re-exported types).
  • compiler.rs is 68% inline tests (1,303/1,906 lines) — acceptable, revisit only if it grows.
  • svsim-render stays a 5-line placeholder by explicit decision.

Recommended order of attack

  1. Gate the negative corpus. Must-fail tests over parts/failing in corpus_gate.rs (failure + stable diagnostic fragment); retire/thin test-fails.sh; fix or delete test.bat.
  2. Fence the parameterization trap. Elaboration rejects overrides feeding frozen constructs unless equal to the default; add parts/failing cases (now gated); document the freeze in hir.rs and the wiki.
  3. Finish frame-native evaluation. Remove build_instance_value_table round-trips via a resolver seam over the indexed frame (const contexts keep the map path). Record step_hz before/after.
  4. Replace clone-and-compare convergence. Use the change tracking the pass already computes; revisit the ×8 budget with measured counts. Expect steps 3+4 to move the slowest suites by an order of magnitude.
  5. Split frontend/sv_parser.rs into module_structure.rs, statements.rs, expressions.rs, literals.rs, loop_unroll.rs using the sim/ pattern.
  6. Thread spans through diagnostics. Convert the ~58 span-less unsupported() sites; prefix evaluator/width errors with module + construct; verify against the gated negative corpus.
  7. Truth-up and close. Fix the stale width.rs wiki row, add a root README.md, add doc examples to Compiler/SimulationSession, refresh ./test.sh reports (capturing new step_hz), move this review to plans/completed/.

Closing assessment

The first campaign paid down debts of organization; what remains are debts of execution: a runtime doing quadratic work through adapter tables it already has the machinery to avoid, a parameterization seam that will silently mis-simulate the first real parameterized core someone imports, and a diagnostic surface with no regression protection. The dominant risk is the runtime's cost curve — it taxes every test run and blocks corpus growth — but the best first move is the cheap verification and fencing work (steps 1–2), which makes the perf surgery (steps 3–4) safe. Expected payoff: a gate measured in seconds, silent-wrong turned into hard errors, and no production file over ~1,000 lines. None of this calls for new architecture — the design is right; the remaining work is finishing what the design already started.

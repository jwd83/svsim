Architectural Review — svsim

Reviewed 2026-07-06 against main @ 94e5ef5 · canonical copy: plans/in-progress/architectural-review.md

Executive summary. The Rust rewrite is structurally healthy where it matters most: the compile pipeline (frontend → HIR → validate → elaborate → design) has clean, owned boundaries, the CLI is genuinely thin, and behavior is pinned by a large corpus-driven compatibility suite. The structural cost is concentrated in two places: sim.rs is a ~5,000-line god module absorbing every runtime concern, and the verification story behind the project's “all green” claims is quietly broken — test.sh never actually tests parts/sap2 (its committed report contains sap1’s results) and parts/sap3 is untested by any script. Order of attack: fix verification first so every later change is provable, then split sim.rs along its existing seams, then consolidate the three parallel expression evaluators.

Interpretation: test coverage is genuinely strong for a simulator at this stage — the risk is not missing tests but that the shell-script layer that runs the corpus and publishes “green” reports has rotted without anything noticing. Secondary cost: the debug-mode suite takes ~4 minutes wall because unit tests execute whole corpus simulations; the corpus gate proposed below should run heavy suites in release or a tiered mode.

Structurally sound elements preserve

  • Owned HIR boundary. sv-parser types never escape crates/svsim/src/frontend/ (verified by grep). The rest of the system programs against hir.rs (474 lines, plain data). The single most load-bearing decision in the codebase — do not let convenience imports breach it.
  • Library-first, thin CLI. main.rs is 242 lines of clap dispatch over library entry points; a 521-line integration test drives the binary end-to-end.
  • Corpus-driven compatibility testing. JSON expectation suites beside the SystemVerilog sources, with a deliberate green/negative split. The four-state and inout campaigns both landed against this corpus without breaking it — the mechanism works.
  • Typed value layers with explicit escape hatches. BitValue (2-state, host-facing) vs LogicValue (4-state, HDL runtime) is a documented, locked decision; _2state wrappers preserve legacy fail-on-x/z behavior explicitly.
  • Maintained knowledge layer. wiki/architecture/ is accurate at the module level and materially shortens onboarding; AGENTS.md rules match the code's actual shape (exceptions noted below).
  • Deliberate deferral of rendering. svsim-render is a placeholder on purpose — nothing here is a reason to build it out early.

Structural risks and costs

rank 1Verification scripts are broken; published reports are stale artifacts

Evidence — test.sh:10 runs parts/sap1 a second time and writes the output to report-parts-sap2.json; parts/sap2 (9 JSON suites) is never executed by the script and its committed “6/6 green” report is actually sap1 data. parts/sap3 (4 suites) appears in no script. Three divergent runners exist (test.sh, test-fails.sh, test.bat); docs/tests/*.json are generated artifacts committed to git with no drift detection.

Consequence — the core invariant “the green corpus is green” is unverifiable by any single command and has silently regressed at least once. Every future slice lands with false confidence.

Fix direction — make the green corpus a cargo test gate using the existing run_json_test_dir API; fix or retire the shell scripts; regenerate the committed reports as part of the gate or stop committing them. No new infrastructure needed.

rank 2sim.rs is a god module absorbing every runtime concern

Evidence — 3,059 implementation lines holding at least seven distinguishable responsibilities: the public SimulationSession API (~280 lines); hierarchical state instantiation (~160); the settle/step scheduler; a full four-state expression interpreter (eval_expr, ~220, plus ~500 lines of logic-bit primitives at sim.rs:2043–2316); lvalue resolution and net-driver staging (~400); $readmem-style memory-file parsing (sim.rs:403–518); the legacy ROM shim (sim.rs:1816–1921); and per-instance parameter elaboration (sim.rs:1921).

Consequence — every runtime feature, fix, and slice lands in the same file; review diffs concentrate there; unrelated changes collide; interpreter primitives can't be unit-tested where they live. The dominant ongoing tax on development.

Fix direction — split into a sim/ module directory along seams that already exist (the file is mostly free functions): value.rs, eval.rs, state.rs, memory.rs, session.rs, moving inline tests with their subjects. No trait abstractions, no new crates.

rank 3Three parallel expression evaluators with divergence risk

Evidence — (a) validate.rs::const_eval_expr + ConstValue, ~400 lines of 2-state constant evaluation (validate.rs:648–1048); (b) sim.rs::eval_expr, the four-state runtime interpreter; (c) frontend/sv_parser.rs::lower_constant_* parse-time folding (sv_parser.rs:432–614). Parameters are additionally evaluated at session-build time via evaluator (b).

Consequence — every new operator or width rule must be kept consistent in up to three places; a constant expression can legally fold differently at compile time than it simulates at runtime; nothing tests the evaluators against each other.

Fix direction — one shared HIR-level constant evaluator used by validation, frontend folding, and parameter elaboration. The runtime interpreter stays separate but shares the primitive bit ops (rank 4).

rank 4Four-state primitives live in the interpreter, not the value layer

Evidence — logic_bit_not/and/or/xor, reductions, shifts, comparisons, slices, sign-extension (~500 lines, sim.rs:2043–2316) operate purely on LogicBit/LogicValue yet live in sim.rs; logic_value.rs (699 lines, well-tested) exposes only construction/inspection.

Consequence — the truth tables that define simulator correctness are tested only indirectly through whole-simulation runs; the const evaluator can't reuse them, which is partly why it reimplements arithmetic on BitValue.

Fix direction — move the primitives into logic_value.rs (or logic_ops.rs) with direct truth-table unit tests. Mechanical and behavior-preserving; shrinks sim.rs as a side effect.

rank 5Elaboration responsibilities are split across three files

Evidence — elaborate.rs (357 lines) computes runtime object shapes but not parameter values; values are computed lazily in sim.rs per session build; validate.rs owns resolve_legacy_rom_data_path (path resolution, not validation) which sim.rs imports. The wiki describes elaborate.rs as “the” elaboration layer, which no longer matches.

Consequence — unclear ownership: a parameter bug can plausibly live in three files; elaboration can't be inspected or cached independently of a live session.

Fix direction — move parameter evaluation into elaborate.rs so ElaboratedDesign carries resolved values; relocate ROM path resolution next to the ROM shim. A re-homing, not a redesign.

rank 6 · deferredString-keyed, clone-heavy runtime state

Evidence — ModuleState keys parameters, signals, memories, and clock state by HashMap<String, …>; port drivers carry cloned Exprs; build_instance_value_table/sync_instance_values_to_frame (sim.rs:1212–1344) maintain a second, name-keyed view of the object frame re-synced every settle pass.

Consequence — two representations of runtime state must stay coherent; per-step hashing/cloning sets a hard performance ceiling. This is the wall picorv32-scale simulation will hit.

Fix direction — explicitly deferred. When picorv32-scale simulation becomes a goal, extend elaboration to assign numeric object ids ahead of time. Do not attempt this rewrite in the current campaign; it would destabilize the corpus for no present-day gain.

Smaller frictions

  • Doc drift: AGENTS.md and the wiki reference a ref/ Python oracle absent from this checkout; AGENTS.md claims “no usable Git history” while the repo has a meaningful one; docs/progress/ stops at 2026-03-20.
  • Plan scatter: plans live at the repo root (plan.md, plan-sap3.done.md), in docs/, and in wiki/roadmap/ with no single lifecycle. This review adopts plans/in-progress/ → plans/completed/.
  • Legacy ROM magic naming contradicts AGENTS.md's “explicit configuration over hidden naming conventions”; fine to keep as a compat shim, but isolate and document it as legacy (covered by ranks 2/5).
  • parts/roms/ is empty; test.bat appears Windows-stale.

Fix test.sh (sap2 typo, add sap3) or reduce it to a thin wrapper; regenerate the committed docs/tests/ reports or remove them in favor of on-demand output.

Full cargo test: 187/187 in ~115s — faster than the old 178-test baseline (~4 min) despite the added gate (unit tests 130s→32s, CLI 92s→11s). Note: there are 9 green part dirs, not 8 as the snapshot said. test.bat left for step 2; committed reports kept-and-regenerated rather than removed.

  2. Truth up the guidance docs. Fix AGENTS.md (ref/ absence, git-history note, test commands), refresh the wiki workspace map and current-state pages against post-sap3 reality, and move root plan files into the plans/ lifecycle.

    Done 2026-07-06, one docs-only commit: AGENTS.md truthed up (stale ref/ and git-history claims removed; gated 9-dir corpus, corpus gate, and opt-level override documented); plan.md → plans/completed/plan-sap2-inout.md and plan-sap3.done.md → plans/completed/plan-sap3.md; nine wiki pages refreshed + log entry appended.   3. Split sim.rs into a sim/ module directory along existing seams: value.rs, eval.rs, state.rs, memory.rs, session.rs, moving inline tests with their subjects. Public API unchanged; behavior-preserving by construction, verified by the step-1 gate.

    Done 2026-07-06 in 6 slice commits, each independently green (1a23287 rename to sim/mod.rs; b91638b value.rs 463; 9da767f memory.rs 283; 1397652 eval.rs 686; 3c7cc8b state.rs 694; 796dec3 session.rs 958 + tests.rs 1,904 with mod.rs down to a 40-line documented root). Function bodies untouched — declarations, pub(super), and glob re-imports only. Full suite 187/187, wall time unchanged. Inline tests moved wholesale to sim/tests.rs; per-subject test migration deferred to steps 4–5.

  4. Move the four-state primitive operations into the value layer (logic_value.rs or logic_ops.rs) with direct truth-table unit tests; sim/eval.rs becomes a consumer.

    Done 2026-07-06 in 3 slice commits: b246902 bit truth tables → new crate-private logic_ops.rs (6 tests, full 4×4 tables); 7fc56ce structural ops (sign-extend / slice / replace-slice, 5 x/z tests); 41d7cc4 reductions retyped to &LogicValue and moved (3 tests). Core unit tests 168→182; full suite 201/201. Value-level combinators stay in sim/value.rs by design — they encode coercion/signedness semantics, not truth tables.

  5. Consolidate constant evaluation into one shared HIR const-evaluator used by validate.rs, frontend folding, and parameter elaboration; delete ConstValue and the frontend's private folding once ported, with regression tests pinning today's accepted/rejected corpus behavior.
  6. Re-home elaboration: move elaborate_module_parameters from sim.rs into elaborate.rs (resolved values on ElaboratedDesign); move resolve_legacy_rom_data_path out of validate.rs next to the ROM shim.
  7. Isolate the legacy ROM shim in its own module with a short doc header stating the naming contract and its legacy status.

Deferred by design: runtime interning/performance work (rank 6) and any build-out of svsim-render — both wait until their milestones are actually scheduled.

Closing assessment

The dominant risk is concentration: one file owns the runtime, and one broken shell script owns the credibility of the compatibility suite. The best leverage point is step 1 — a single cargo test that truthfully proves the corpus green — because it converts every subsequent refactor from “careful” to “mechanical.” After the split and consolidation steps, the expected payoff is that new language features touch one evaluator and one runtime module instead of three evaluators inside a 5,000-line file — and that “all green” means what it says.
